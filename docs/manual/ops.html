Only two assets ever leave the machine — one was added 2026-09-12

Every other skill finishes locally. These two cross the boundary, and both require consent first.

AssetWhat leavesCostConsent
/codex-claude-loopPlan text or a git diff — never the whole treeCovered by the subscriptionEvery time — not recorded
/image-generatorThe image prompt only — source never leavesBilled separately from the subscriptionOnce per project → assets.imageProvider in orangekit.config.json
/image-generator is the harness's first paid external call. So it holds three lines — ① it shows the price as a number before asking you to choose ("this costs money" is not something you can decide on) ② it validates size, quality and format before the call, so bad input never costs anything ③ it reports the response's usage verbatim afterwards — the bill rests on a measurement, not an estimate.

The key is never stored. Only the OPENAI_API_KEY environment variable is read — writing it into .env, orangekit.config.json or a shell profile is blocked by this harness's own security-check. No key means undecidable (exit 2), not blocked — it falls through to hand-off mode and writes a prompt a human can paste into ChatGPT (invariant ①).

  • skills/ listing ↔ graph nodes

Change a graph number and fix four documents with it — README.md · harness-anatomy.md (two places) · operations-manual.md. Skip it and --default fails. That is the feature.

What common.sh gives you — use only these

root and numbers

  • orangekit_root() — never BASH_SOURCE or dirname ../... Exits 2 if the root cannot be settled
  • orangekit_num() — never || echo 0
  • orangekit_count_lines()

output — it hides the event contract

  • orangekit_emit_context()
  • orangekit_emit_block()
  • orangekit_emit_notice()
  • Unsupported fields are silently ignored — which is why you never hand-write the JSON

state and telemetry

  • orangekit_state_dir() · orangekit_handoff_dir()
  • orangekit_heartbeat() · orangekit_edge() — writes an edge into graph.log
  • orangekit_worktree_snapshot()

Verify before you assert. Before assuming "Claude Code behaves this way", read docs/platform-contract.md. If it isn't there, check the official docs and add it with the source URL and the date you checked — never from memory. Without this discipline, hand-rolled substitution variables that are never expanded grew to 28 places.

Self-repair

The harness measures and repairs itself

A third loop — re-checking the built-ins (P6-②)

Built-ins keep getting better along with the model. So "is this custom asset still necessary?" is not a question you ask once.

VerdictWhat it means
Replace with nativeThe built-in is now enough — retire the custom asset
Keep customIt covers ground the built-in does not — write down why
ComposeThe custom asset must be a thin layer wrapping the built-in, and must not reimplement what the built-in already does
Both conditions must hold to skip it — the last verdict is within 30 days and there have been zero harness-asset commits since. The date alone is not enough.

Invariants

These never break

  • Cannot-determine is not a blockfalse positive → the user turns the hook off → blocking power 0
  • Never make a copy (one source + references)drift — the failure mode that killed v2
  • Verify the path of reach697 lines of rules reached nobody for four months
  • A blocking device proves it blocks — for the intended reasona dead device pretending to be alive
  • Numbers in documents are machine-checkedfalse statements get shipped
  • Never touch the consumer's own files unaskedloss of trust
  • Existing code patterns beat the plugin's guidesthe harness silently overwrites the project
  • The safety floor can only be raised by a projectthe safety devices become bypassable

⑦ and ⑧ are a pair — two layers pointing in opposite directions

LayerWhat it coversThe rule
safety floorreversibility class · verification duty · secret boundary · decision pointsA project can only raise it. Lowering it requires an explicit request from the user
How to raise it: drop files into .claude/resources/ and the skills read them automatically
procedure & formstack conventions from the guide packs · skill workflows · naming · document formatThe project wins. Order: the user's request → the project's CLAUDE.md → the project's .claude/rules/ → the repository's existing code patterns → the plugin's guides
"Existing code patterns beat the plugin's guides" is the load-bearing half. When a guide recommends one shape and the repository actually uses another, follow the repository. Changing an existing pattern on the strength of a guide is a refactor, and refactors happen when someone asks for one.

Fold cannot-determine into blocking and you get a false positive,
a false positive makes the user turn the hook off,
and a hook that is off blocks nothing.

Limits

Some things cannot be checked here

This repository has no consumer. So whether a rule actually arrives in a consumer project cannot be verified from here. Every self-check can pass and that question stays unanswered.

What to confirmHowWhy

False positives in the first sessionopen one session right after a fresh installThe hook roll-call used to count "had no chance to run" as "did not fire"
What never gets created in this repo — orangekit.config.json · dev/active/ · stack guides. This is the plugin source, not a consumer project. rules/ is an asset to be shipped, not configuration that loads here — which is exactly why a separate CLAUDE.md exists.
