# FastAPI + SQLAlchemy (async) core card

The project spec (`dev/docs/api/` etc.) and `.claude/rules/code-conventions.md` take precedence over this card and the `backend-guide` skill.
Verified versions — `fastapi@0.141` · `sqlalchemy@2` · `pydantic@2`. Install the latest stable release (`code-change.md` "Before Adding a Dependency") — where an item conflicts with a newer major, the official upgrade docs take precedence.
Look up wiring and examples in the `backend-guide` skill when needed.

## Consistency — the project decides the values

- [consistency] Path prefix · id type · envelope · validation-failure status code follow existing code or the spec; if there is none, decide once and write it in `code-conventions.md`. — why models get it wrong: it anchors on FastAPI's default (422) or the guide example values <!-- evidence: guide-skeleton "Stack core card" · guide-ab T-B (fastify pack 422) · model-gap: not-observed -->
- [consistency] Routers never raise `HTTPException` directly; they raise the project error and one mapping table decides the status, looked up with `.get(code, 500)`. — why models get it wrong: raised directly, the envelope has two shapes, and a subscript `KeyError` erases the cause <!-- evidence: policies seam-no-http-exception · seam-status-lookup · model-gap: not-observed -->

## Security — where this stack leaks

- [security] Never use an ORM model as `response_model`; use response-only schemas. — why models get it wrong: a column added later silently rides into the response <!-- evidence: policies no-orm-in-response · model-gap: not-observed -->
- [security] Get the principal only through the one auth dependency (`Depends`). Routers never parse the token themselves. — why models get it wrong: that makes two boundaries, and two always drift apart <!-- evidence: policies seam-depends-current-user · model-gap: not-observed -->

## Performance & integrity — what breaks silently

- [performance] Build a partial update with `model_dump(exclude_unset=True)` and reject `null` or an empty body with 422. — why models get it wrong: fields not sent overwrite the stored value with defaults, and the syntax is flawless <!-- evidence: resources/input-validation.md (run-verified) · policies partial-update-exclude-unset · model-gap: not-observed -->
- [performance] Use only `async_sessionmaker(expire_on_commit=False)` and load relations up front with `selectinload` and the like. — why models get it wrong: a lazy load under async is not slow, it is a `MissingGreenlet` 500 <!-- evidence: resources/data-access.md §1·§6 (run-verified on 2.0.52) · policies no-sync-session · model-gap: not-observed -->
- [performance] Commit in one place, the session dependency, and catch constraint violations at `flush()` inside the handler. — why models get it wrong: an exception raised after `yield` is not caught by the exception handlers <!-- evidence: policies (what humans keep) · resources/data-access.md (fastapi 0.141 measured) · model-gap: not-observed -->
- [performance] Judge a uniqueness violation by the SQLSTATE of `exc.orig`. — why models get it wrong: `isinstance(exc.orig, UniqueViolationError)` is `False`, and message strings change with locale and version <!-- evidence: resources/error-handling.md (run-verified) · policies no-string-sqlstate · model-gap: not-observed -->
- [performance] Read and fix an Alembic autogenerated revision before committing it, and never mix DDL and a backfill in one revision. — why models get it wrong: a composite index goes missing, or a failed backfill desyncs stamp and schema and blocks the rerun <!-- evidence: policies (what humans keep) · resources/migrations.md (measured) · model-gap: not-observed -->
