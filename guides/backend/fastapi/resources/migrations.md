# Migrations — code that runs at deploy time

Owns all of `alembic/`: `env.py` wiring · the limits of autogeneration · expand-contract · backfill · deploy order.
**Defining** the schema (`Base`·`Task`·indexes) is owned by `resources/data-access.md`, process startup
(`create_app`·`lifespan`) by `resources/project-structure.md`, and health checks, the pool, and observability by
`resources/operations.md`.

> **This is the one context that is an exception to the ownership discipline.** The first principle of this axis is "ownership lives in the `WHERE`", but
> a migration runs on a deploy rather than a request, so **it has no subject and it targets the rows of every owner** —
> the absence of `owner_id` in this file's `WHERE` clauses is normal, and it is normal **only here**.

> **Migrations run at deploy time, not at request time.** A query runs hundreds of times a second and can be
> reversed, but a migration runs once and **cannot be reversed after it has erased data.** Different lifetimes mean
> different discipline — committing an autogenerated revision without reading it is the one habit this file blocks.

## 1. Decision tree — do you leave this change to autogeneration

| what changes | how to decide |
| --- | --- |
| **adding** a table, column, or index | use the autogenerated draft. Read and confirm the index names only |
| **renaming** a column | **write it by hand.** Autogeneration emits `add_column`+`drop_column` and does not move the values (§3) |
| type change · tightening to `NOT NULL` | existing rows have to satisfy the new constraint — the backfill comes **first** (§4·§5) |
| **dropping** a column | **split it across two deploys.** The old code still reads that column (§4) |
| adding or changing a `server_default` | **write it by hand.** Autogeneration does not see it under the default settings (§3) |
| data-only change (backfill) | split into **a separate revision** from the DDL (§5) |
| adding an index to a large table | `CONCURRENTLY` + `autocommit_block` (§6) |

**Autogeneration is a draft, not a result.** The rows above that resolved to "write it by hand" are not places where
autogeneration **emits something wrong** but where it **emits something plausible** — the syntax is perfect, it runs,
and the data disappears. That is why opening the file in `alembic/versions/` right after generating it is part of the steps
(`PACK.md` Quick Start, step 2).

## 2. Wiring (`alembic/env.py`) — running synchronous Alembic on top of an async engine

Alembic's migration execution is **synchronous**. This axis's engine is async, so `connection.run_sync()` carries the
synchronous function on top of the async connection. The connection string comes only from `settings` — the
`sqlalchemy.url` in `alembic.ini` is left empty and `env.py` overwrites it (policy `env-single-entry`).

<!-- file: alembic/env.py -->
```python
import asyncio

from alembic import context
from sqlalchemy import pool
from sqlalchemy.engine import Connection
from sqlalchemy.ext.asyncio import async_engine_from_config

import app.db.tasks  # noqa: F401  — without it metadata is empty and autogeneration reports "no change"
from app.db.base import Base
from app.settings import settings

config = context.config
config.set_main_option("sqlalchemy.url", settings.DATABASE_URL.replace("%", "%%"))
target_metadata = Base.metadata


def _run(connection: Connection) -> None:
    context.configure(connection=connection, target_metadata=target_metadata)
    with context.begin_transaction():
        context.run_migrations()


async def _main() -> None:
    engine = async_engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.", poolclass=pool.NullPool,   # a migration needs no pool
    )
    async with engine.connect() as connection:
        await connection.run_sync(_run)     # run synchronous Alembic on top of an async connection
    await engine.dispose()


asyncio.run(_main())
```

**The single line `import app.db.tasks` is the premise of autogeneration.** `Base.metadata` is filled when the model module is
imported, so without this line `Base.metadata.tables` is `[]` and autogeneration reports **not "there is nothing"
but "no change"** — that is, a silent pass rather than a failure. Before the import it is `[]` · after, `['tasks']`,
and the autogenerated body produced in that state was a single `pass`.
<!-- verified: alembic 1.19.1 · deleted the import from env.py and ran revision --autogenerate; the upgrade body was pass. Restoring it produced create_table (positive control) -->

**`.replace("%", "%%")` is not decoration.** `set_main_option` puts the value into ConfigParser, and
ConfigParser reads `%` as interpolation syntax — a DSN whose password contains `%` dies with
`ValueError: invalid interpolation syntax` **at migration time, not at boot.** This pack reads the connection
string in one place only, `settings` (policy `env-single-entry`), so this path is the only route.
<!-- verified: alembic 1.19.1 · reproduced with the DSN `…u:p%ss@db…` — without escaping, ValueError (position 24); with `%%` it reads back identical to the original. Also confirmed the value is unchanged when applied to a DSN with no `%` (regression) -->

The file above holds **the online mode only**. If you need `--sql` (offline) output, add a `context.is_offline_mode()`
branch — this pack's deploy path is an online run, so it is not in the base shape.

## 3. What autogeneration cannot see

| what autogeneration does | what autogeneration **cannot** do |
| --- | --- |
| adds tables, columns, indexes; adds and drops named constraints; type changes | **renaming a column** — it comes out as `add_column`+`drop_column`. The new column is created as `NULL` and the old values are not moved |
| adds and drops indexes (based on the `Index(...)` declaration) | **data migration and backfill** — it only looks at schema differences, never at rows |
| — | **`server_default`** — it is not compared under the default settings. Pass `compare_server_default=True` and it produces `alter_column`, but per-dialect reliability is low, so this pack does not turn it on <!-- verified: alembic 1.19.1 · planted a server_default on the model and generated under both settings — the default gives a pass body, the flag gives alter_column. Proxied on SQLite; PG dialect reliability unverified --> |

Renaming is the most expensive. Change only the model from `title` to `label`, run autogeneration, and these two come out.

```python
# ❌ exactly as autogeneration emitted it — it runs, and the data disappears
op.add_column("tasks", sa.Column("label", sa.String(200), nullable=True))
op.drop_column("tasks", "title")
# ✅ fix it by hand — rename only, and the values come along untouched
op.alter_column("tasks", "title", new_column_name="label")
```

Insert one row (`title='original value'`), run the two statements above as-is, and `label` becomes `NULL` while `title`
disappears — **it ends in success, not failure.**
<!-- verified: ran both shapes against a table holding values and read it back — add_column+drop_column turned 'original value' into None, while alter_column(new_column_name) kept 'original value' and even survived a downgrade round trip (positive control). Proxied on SQLite -->

The case that comes out as `nullable=False` is different. Adding a `NOT NULL` column with no default to a table that has
rows is **refused by the DB** — which is why a rename erases data "silently" only when the new column
allows `NULL`. The two cases differ, so always read the `nullable` of the generated output.
<!-- verified: proxied on SQLite — aborted with "Cannot add a NOT NULL column with default value NULL". PG's wording and behavior unverified -->

## 4. Expand-contract — during a rolling deploy two versions of the code see the same DB

**Schema and code do not change at the same moment.** While the deploy runs, old pods and new pods are alive together,
so move **only in directions that can be reversed**, one at a time.

| step | what it does | what is running then |
| --- | --- | --- |
| 1 expand | **add** the column and the index. Do not put `NOT NULL` on it yet | old code (it does not know the new column) |
| 2 deploy | ship the code that reads **and writes** the new column | old and new mixed |
| 3 fill | fill the remaining rows in batches (§5) | new code |
| 4 tighten | apply the `NOT NULL` and unique constraints | new code |
| 5 contract | drop the old column **in the next deploy** | new code only |

**Merge 1 and 4 into one revision and step 2 disappears.** The old code does not put a value into the new column, so
applying `NOT NULL` immediately makes every `INSERT` from an old pod fail — it blows up most painfully at the point where
the deploy is about half done. Pull 5 forward and, conversely, an old pod's `SELECT` reads a column that is gone.

Contraction is the **next deploy**. Its purpose is to leave room for a rollback, so even after step 4 is done you wait
one deploy before dropping.

## 5. Backfill — check the `rowcount`

**0 rows is not success; usually it means the condition is wrong.** A backfill can quietly do nothing and still finish
green, so count the updated rows and stop at 0. The `priority` below is **an example-only column added as step 1
of §4** — it is not on the `Task` model (see the ledger's "symbols appearing in examples").

```python
# alembic/versions/xxxx_backfill_priority.py — excerpt
BATCH = 1000

def upgrade() -> None:
    bind = op.get_bind()
    total = 0
    while True:                       # do not lock every row with a single statement
        result = bind.execute(sa.text(
            "UPDATE tasks SET priority = 0 WHERE id IN ("
            " SELECT id FROM tasks WHERE priority IS NULL LIMIT :n)"), {"n": BATCH})
        if result.rowcount == 0:      # no rows left to fill — normal termination
            break
        total += result.rowcount
    if total == 0:                    # not one row was found — suspect the condition
        raise RuntimeError("backfill matched 0 rows — check the condition")

def downgrade() -> None:
    # There is nothing to reverse: the old values were kept nowhere, so they cannot be restored.
    # This revision produced no DDL — the previous revision reverses the schema.
    pass
```

The reason it runs in batches is locking. If one `UPDATE` touches every row, writes back up behind that transaction
until it ends. Cut it with `LIMIT` and each batch locks briefly and finishes.

With a 3-row seed, after `total 3` the next batch terminated normally at `rowcount == 0`, and changing the same
migration's condition to a wrong value gave `total 0` and a `RuntimeError` that stopped the deploy — **both the
positive and the negative case were confirmed with the same script.**
<!-- verified: alembic 1.19.1 · with a 3-row seed, 3 updated → next batch 0 and termination. Changing the WHERE to an unmatchable condition gave 0 updated → RuntimeError. Proxied on SQLite -->

**Do not mix DDL and a backfill in one revision.** Whether the preceding DDL is reversed together when the backfill
fails midway depends on the DB's transactional DDL support, and when it is not reversed you are left with **a version stamp on
the old revision while the schema has already changed**, which blocks a re-run. That is exactly what happened, measured:
the stamp went back to the previous revision but the added column remained, and re-running it died with
`duplicate column name`.
<!-- verified: proxied on SQLite (aiosqlite) — after the failure, alembic current showed the previous revision while PRAGMA table_info still had the column. PostgreSQL's transactional DDL behavior unverified -->

## 6. `CREATE INDEX CONCURRENTLY` — it has to be called outside a transaction

Put a plain `CREATE INDEX` on a large table and **writes are blocked** while the index is being built. PostgreSQL's
`CONCURRENTLY` avoids that but **does not run inside a transaction block**, and Alembic wraps a migration in a
transaction. So `autocommit_block()` steps out of it for that stretch only.

**This is the shape for adding an index late to a table that is already in production.** The base shape's
`ix_tasks_owner_created_id` (the premise of keyset pagination) is declared by `data-access.md` in `__table_args__` and
**created by the autogeneration of the initial revision** — the table is empty, so there are no writes to lock. Below is the case where
`status` lookups got slow later and a new index is added.

```python
# alembic/versions/xxxx_add_status_index.py — excerpt
def upgrade() -> None:
    with op.get_context().autocommit_block():   # inside here is outside the transaction
        op.create_index("ix_tasks_owner_status", "tasks", ["owner_id", "status"],
                        postgresql_concurrently=True, if_not_exists=True)

def downgrade() -> None:
    with op.get_context().autocommit_block():   # the drop rides the same discipline
        op.drop_index("ix_tasks_owner_status", "tasks",
                      postgresql_concurrently=True, if_exists=True)
```

We compared that `postgresql_concurrently=True` really compiles to `CREATE INDEX CONCURRENTLY` on the PG dialect
and that the same index without the flag comes out as `CREATE INDEX`. `autocommit_block` lives on
`MigrationContext`.
<!-- verified: compared CreateIndex compilation only, on the sqlalchemy 2.0.52 postgresql dialect (positive and negative) · confirmed alembic 1.19.1 MigrationContext.autocommit_block exists. **Server execution unverified** -->

**What is inside `autocommit_block` does not roll back.** A failure in that stretch can leave the index in an `INVALID`
state, and then you drop it and build it again — which is why this revision holds nothing else.
<!-- unverified: no PostgreSQL server — the actual state transition of an INVALID index was not observed -->

## 7. When to run it — `upgrade head` is a deploy step

**Do not run it from an app startup hook.** When N pods come up at once, N of them grab the same migration, and all but
the first to grab it fail or wait. A failure makes that pod count as having failed startup and it enters a
restart loop — one migration shakes the whole deploy. <!-- unverified: the multi-pod race was not reproduced against real infrastructure -->

Pull it out as **a separate step** of the deploy pipeline: one migration job runs `upgrade head` to completion, and
only then does the new code roll out. Step 1 of §4 is that job.

**Downgrade is not a deploy tool.** The place to use `downgrade()` is **the round-trip test in local and CI**
(§8), and it is not expected to be the means of reversal in production — the inverse of `drop_column` only restores
the column, **not the values.** So:

- **Do not leave `downgrade()` empty** — the round trip in §8 will not run
- For a revision that erases data, state in a comment in `downgrade()` that it cannot be restored
- Production reversal is not a downgrade but **the expand-contract of §4**. That is why contraction is deferred

## 8. Testing a migration — the round trip and an empty diff

```bash
uv run alembic upgrade head      # apply
uv run alembic downgrade -1      # reverse just the one revision you wrote
uv run alembic upgrade head      # again — all three have to succeed
uv run alembic check             # a mismatch between model and schema surfaces here
```

**The two values play different roles.** What runs each time you write a revision is `downgrade -1` (does the one you just
wrote come back), while the **full round trip** CI runs is `downgrade base` → `upgrade head` (does everything rewind from the
first revision). The measurement below is the latter.

`alembic check` **leaves no artifact** and only decides drift. Clean, it prints
`No new upgrade operations detected.` with exit code 0; mismatched, `FAILED: New upgrade operations
detected: [...]` with a **non-zero exit code** — so it can be used directly as a CI step.
We planted one column on the model to confirm the failure and reverted it to confirm the pass.
<!-- verified: alembic 1.19.1 · planted drift → FAILED + exit code 255 (positive control), reverted → pass + 0. Proxied on SQLite -->

What the round trip catches is **whether `downgrade()` actually runs**, and what `check` catches is **whether the model and the
migration describe the same schema**. They catch different defects, so one does not substitute for the other — a hand-fixed
autogenerated revision easily fixes only `upgrade()` and leaves `downgrade()` alone, and that defect shows up only in the round trip.

We confirmed that after the round trip `upgrade head` → `downgrade base` → `upgrade head`, `check` passes, and that in
that state `revision --autogenerate` produces a body of a single `pass` (an empty diff).
<!-- verified: alembic 1.19.1 + sqlalchemy 2.0.52 + aiosqlite 0.22.1 · ran the four commands above in order. The PG round trip is unverified -->

**The test suite does not substitute for this verification.** The test DB in `resources/testing.md` is built with
`Base.metadata.create_all` and never runs a migration once — so the four commands above have to be
**a CI step separate from pytest**, and without them no migration defect can turn any green red.

## Misuse list ① — synchronous Alembic template → async shape

| old habit (synchronous template) | current shape (async engine) |
| --- | --- |
| `engine_from_config` + `with connectable.connect()` | `async_engine_from_config` + `await connection.run_sync(...)` |
| autogenerating with `target_metadata = None` | import the model module + `target_metadata = Base.metadata` |
| writing the connection string into `sqlalchemy.url` in `alembic.ini` | `env.py` overwrites it with `settings.DATABASE_URL` |
| `alembic upgrade head` from a startup hook | pull it out as a separate step of the deploy pipeline |
| committing an autogenerated revision without reading it | open it, read the `nullable`, the index names, and whether it is a rename, and fix it |

## Misuse list ② — confusable pairs

| commonly picked wrong | the exact condition for applying it |
| --- | --- |
| `alembic check` vs `revision --autogenerate` | **deciding** drift is the former (it leaves no file), actually **writing** is the latter |
| `downgrade -1` vs `downgrade base` | testing **the one preceding revision** is the former, verifying **the full round trip** is the latter (§8) |
| contracting right after expanding vs contracting in the next deploy | while old code is alive during a rollout, contraction is the next deploy |
| `alter_column(new_column_name=…)` vs `add_column`+`drop_column` | a pure rename is the former. The latter does not move the values |
| DDL and backfill in one revision vs split | split them. Mixed, a failure splits the stamp from the schema |
